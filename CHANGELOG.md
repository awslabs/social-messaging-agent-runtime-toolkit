# Changelog

All notable changes to SMART, the Social Messaging Agent Runtime Toolkit, are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions are calendar-based, `YYYY.MM.patch`, so `2026.10` is the release line of October 2026, `2026.10.0` is its first release, and `2026.10.1` would be a fix to it; the version lives in the `VERSION` file at the repository root and nowhere else. The admin console has its own heading under each release because a console-only release is a real case.

## [Unreleased]

### Added
- The `smart-socialagent` wheel ships the stack's Terraform (`infra-terraform/` with `bootstrap/` and `modules/`; not `tftest/`, state, tfvars, lock files or `.terraform/`). Outside a SMART checkout, the CLI copies it into the project's `.socialagent/infra/<version>/` and replaces the copy whenever its content differs from what the CLI ships, so edits there are overwritten; Terraform's local state in it (`bootstrap`'s) is kept. Every command that runs Terraform or reads its variables resolves the root the same way: `--tf-dir`, then the nearest SMART checkout's `infra-terraform/` (unchanged for contributors; a checkout is an `infra-terraform/main.tf` with `pyproject.toml` and `src/socialagent/` beside it, so another repository's `infra-terraform/` above the project is passed over), then that copy. From a pip install every command works without a checkout, `deploy` and `destroy` included ([#133](https://github.com/awslabs/social-messaging-agent-runtime-toolkit/issues/133)).
- Package mode: with no SMART checkout above the Terraform root (the managed copy, or a `--tf-dir` elsewhere), the Lambda layer and the template sync install the SDK in CodeBuild from the package index instead of building it from the checkout's source. `deploy` and `destroy` pass the CLI's own distribution at its own version (`sdk_package_spec`, which must be an exact `<name>==<version>` pin), and pip installs wheels only (`--only-binary=:all:`). `deploy --sdk-wheel <path>` installs a local wheel instead (`sdk_wheel_path`), uploaded to the stack's build artifacts under a key carrying its MD5, to test a build before it is published; its dependencies still come from the package index. A checkout builds exactly as before, and a stack deployed from one plans no change. Package mode installs from PyPI inside the deploying account, so a CLI version can deploy from a pip install only once that version is published, and the change wants a security review before it is relied on ([threat model, M34](docs/threat-model.md#m34-ci-supply-chain-actions-pinned-to-commit-shas-dependency-updates-on-a-cooldown)).
- `bootstrap` (when the backend is missing), `deploy`, `destroy`, `status --refresh` and `config sync` check that `terraform` is on `PATH` before they run anything, and `deploy` (except `--plan`) that the `aws` CLI Terraform's provisioners call is too, naming what is missing, instead of failing at the first call or, for `aws`, partway through an apply.
- The `socialagent` package also installs the agent runtime as the import package `socialagent_runtime`, built from `packages/socialagent-runtime/`, so `import socialagent_runtime` works after a `pip install` and in a checkout after `uv sync`. Its third-party dependency comes with the new `runtime` extra, `pip install "socialagent[runtime]"`, which asks for the same `bedrock-agentcore[strands-agents]` as the blueprints' `requirements.txt`; a plain install stays as light as before. The Lambda layer leaves the package out, so a Lambda still cannot import it. The pyproject change gives the Lambda layer a new source hash, so a stack's next deploy rebuilds the layer once with the same contents.

### Changed
- New projects get `socialagent_runtime` from the package instead of a copy ([#132](https://github.com/awslabs/social-messaging-agent-runtime-toolkit/issues/132), per proposed [ADR-0012](docs/adr/0012-lifecycle-from-the-package.md)). `socialagent init` no longer copies `socialagent_runtime/` into the project; it appends `socialagent[runtime]==<CLI version>` to the project's `requirements.txt` (the distribution and version the CLI is installed as), and the blueprints' Dockerfiles no longer copy the runtime: they copy `requirements.txt wheels*` and install `-r requirements.txt` with any wheel the build put in `wheels/`. The agent therefore installs the release the CLI is, from the package index, so a project builds only once that version is published; to deploy an unreleased build, pass `--sdk-wheel <wheel>`, which the agent build now installs too (uploaded under the agent build's own prefix, so no IAM change), and whose version must be the one `requirements.txt` pins (`deploy` checks before running anything). From a pip install, `pip install -r requirements.txt` in the project gives `socialagent dev` the runtime; without it, `dev` names that install instead of failing with a traceback.
- `socialagent deploy` from a SMART checkout builds the checkout's wheel (`uv build --wheel`, falling back to `python -m build`) into the project's `.socialagent/sdk-wheel/` and passes it as `--sdk-wheel` would, whenever the project pins the SDK, because the version it pins is the checkout's, which no index may have. This moves the checkout stack's Lambda layer and template sync from the repo-tree build to the wheel, and both rebuild once on the first such deploy; the wheel builds reproducibly, so later deploys of an unchanged checkout rebuild nothing. A checkout project that still ships a copied runtime gets no wheel and builds exactly as before.
- `socialagent runtime status` and `runtime update` are now the move to the package. `status` reports whether `requirements.txt` pins the package at the CLI's version, a leftover `socialagent_runtime/` (classified current, outdated or unknown against the CLI's git lineage, as before) and a Dockerfile line still copying it, and exits 1 unless the project has none of these left and is pinned to the CLI. `update` backs the copy up under `.socialagent/runtime-backups/` and removes it, adds the pin (or moves an existing one, in place), and rewrites the Dockerfile only where it holds the exact lines the blueprints shipped; any other line copying the runtime stops it before anything changes, and a different install line is left alone with instructions printed. An unknown copy still needs `--force`. On a migrated project it only moves the pin. `dev` and `deploy` warn about each of these, and never block. The agent's version-mismatch error now points at `socialagent runtime update`.
- The agent archives leave out `wheels/` always, and a `socialagent_runtime/` once `requirements.txt` asks for the SDK's `runtime` extra and the Dockerfile no longer copies it; the zip build never merges a copy over a runtime pip installed. **Migrating an existing project:** upgrade the CLI, run `socialagent runtime update` in the project (from a pip install, then `pip install -r requirements.txt`; from a checkout, `uv sync`), and deploy. Before the update, a stack whose project still carries its copy deploys as it did: its agent archive and image are unchanged and keep running the copy, a Docker stack's CodeBuild project is unchanged, and a zip stack rebuilds its package once, with the same contents, because its buildspec changed. After it, the agent archive changes (the copy, the pin and the Dockerfile), so the image or zip package is rebuilt once with the runtime from the package: from PyPI at the CLI's version from a pip install (which must be published, or pass `--sdk-wheel`), or from the checkout's wheel from a checkout, where the Lambda layer and template sync also rebuild once, as above. Run `stop-runtime-session` for a session you test with, or wait for it to end, as after any agent deploy.

### Fixed
- `personal-assistant` now passes `transcribe_languages` to the transcription call in its `on_media` hook, so the setting applies to its voice notes as it does to the default path. `handlers/` is project code, so an existing project adds `language_options=config.transcribe_languages,` to the `transcribe_audio` call in `handlers/webhook.py` by hand. The blueprint's YAML sets `transcribe_languages: [es-MX, en-US]`, which had no effect on its voice notes before this fix, so check that the list names your users' languages before you deploy the change.
- The zip-mode agent archive leaves out the project's `infrastructure/` directory, like the Docker-mode archive. A zip-mode project with that directory gets a new archive hash, so its next deploy rebuilds the package once.

### Admin console
- The conversation viewer's "Delete conversation" asks for confirmation inside the viewer, naming the conversation and warning that the deletion cannot be undone, before it deletes the conversation's AgentCore Memory events; one click no longer deletes.
- The Stack Detail Deploys tab reports a failed CodeBuild read instead of showing an empty history, reads each stack's builds in the stack's own region, and reads a zip stack's builds from `<prefix>-agent-zip-build`.

### Developer experience
- Published on PyPI as `smart-socialagent` ([ADR-0008](docs/adr/0008-pypi-distribution-name.md)): `socialagent` collides with an existing project there. The command and the import package stay `socialagent`. The package page (`PYPI.md`) opens with the beta and "AS IS" notice.
- A Release workflow publishes to PyPI from a GitHub Release, through trusted publishing and a `pypi` environment with required reviewers; `CONTRIBUTING.md` has the steps.

## [2026.10.0] - 2026-11-05

The first public release. Everything below was in the toolkit when it was published.

### WhatsApp channel
- Outbound message types: text, buttons, list menus, image, document, audio, video, sticker, location, location request, CTA URL, address request, call button.
- Inbound text, media, interactive replies (button, list row, form) and the typing indicator.
- Audio transcription on inbound voice notes.
- Templates: body-only templates in the UTILITY, MARKETING and AUTHENTICATION categories, synced on deploy, with local validation of the rejection causes Meta publishes; a rejection fails the deploy.
- Message buffering: rapid inbound messages are debounced into one agent turn.
- A per-user rate limit, when the state table is enabled.

### Agent runtime
- Recurring and one-shot schedules owned by phone, with ownership read from one field of the schedule name, restricted operation names, a cron floor and a per-user cap.
- External events through API Gateway with an API key and a secret, with credentials sent only to this account's API bound to the key.

### Developer experience
- The `socialagent` CLI: `init`, `dev`, `recipe`, `templates`, `config`, `bootstrap`, `deploy`, `destroy`, `status`, `secrets`.
- Three blueprints (`minimal`, `personal-assistant`, `appointment-scheduler`) and three recipes (`rich-messages`, `voice-reply`, `generate-image`), copied into a project as files.

### Operations
- Security review follow-ups: the SNS certificate URL is parsed, not matched; the WhatsApp envelope is pinned; media roots are allowlisted; invocation logs carry metadata only; roles are scoped to the stack's media keys; console authorization is single-layered.
- Dependabot with cooldowns on every ecosystem: pip, npm, GitHub Actions, Terraform.
- An anonymous deployment counter: one CloudFormation marker stack per deployment, stated in the README and printed by `socialagent deploy`, and turned off with `terraform.enable_deployment_metrics: false`.
- `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`, `NOTICE`, and Apache-2.0 license headers on every file.

### Admin console (beta)
- Fleet view, conversations, per-user state, schedules, templates with preview, logs, errors, restart, phone binding; Cognito sign-in with MFA; deny-by-default authorization on every route. The console has had less production time than the SDK and CLI and ships as beta; it is a separate Terraform root an adopter may skip.
